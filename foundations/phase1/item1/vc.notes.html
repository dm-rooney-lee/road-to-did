Phase 1 / Item 01 — W3C Verifiable Credential Data Model 2.0

Phase 0 built the primitives (signing, JWS, OIDC). Phase 1 starts layering W3C identity standards on top. The first artifact: a Verifiable Credential — a structured JSON document an issuer signs and a verifier later checks. This lab implements VCs in their VC-JWT form, the simplest of the two securing mechanisms VCDM (Verifiable Credential Data Model) 2.0 supports.

Background — read first

The Issuer / Holder / Verifier triangle

SSI (Self-Sovereign Identity)'s foundational diagram. Three roles, three different responsibilities, and a credential that travels through all of them.

Issuer

The party with authority

University, government, employer. Signs the credential with its private key. Publishes its public key so verifiers can check signatures later.
Holder

The party holding the credential

Usually the end-user via a wallet app. Stores credentials, decides when to present them to which verifier.
Verifier

The party that consumes the credential

Employer checking degree, store checking age. Fetches issuer's public key, verifies signature, decides whether to trust.

What changes vs OIDC

In OIDC (Phase 0 Item 04), the OP is online during every login. The RP talks directly to the OP, the OP authenticates the user, the OP issues a token, the RP verifies. Two parties, both online.

In VC, the issuer is online only at issuance time. After that:

  • The credential lives in the holder's wallet
  • The holder presents it to verifiers without involving the issuer
  • The verifier only needs the issuer's public key, not a live connection to the issuer

That's what "decentralized" means here: the trust chain (issuer's signature + public key lookup) replaces the live connection. Useful for credentials that need to work offline (mDL at a bar) or across organizational boundaries (university → employer).

The minimal VC, field by field

Per W3C VC Data Model 2.0. Required fields are highlighted.

{
  "@context":          ["https://www.w3.org/ns/credentials/v2"],
  "id":                "urn:uuid:..." ,
  "type":              ["VerifiableCredential", "UniversityDegreeCredential"],
  "issuer":            "did:example:university",
  "validFrom":         "2026-09-01T00:00:00Z",
  "validUntil":        "2031-09-01T00:00:00Z",
  "credentialSubject": {
    "id": "did:example:alice",
    "degreeType": "BachelorDegree",
    "name": "Alice Doe"
  }
}
FieldRequired?Meaning
@context Required Array. First element MUST be "https://www.w3.org/ns/credentials/v2". Defines the semantic meaning of every other field (see JSON-LD tab).
id Optional Identifier for THIS credential instance. Typically a URN UUID. Allows referencing a specific credential (for revocation, storage keys, etc.).
type Required Array. MUST contain "VerifiableCredential". Additional types (like "UniversityDegreeCredential") describe what kind of credential this is — for routing, validation, display.
issuer Required Identifier of the party that issued the credential. Usually a DID URL (did:example:...) or an HTTPS URL. The verifier uses this to look up the issuer's public key.
validFrom Optional ISO 8601 datetime. Credential is not valid before this. (VCDM 1.x called this issuanceDate.)
validUntil Optional ISO 8601 datetime. Credential expires at this point. (VCDM 1.x called this expirationDate.)
credentialSubject Required Object. The actual claims about the subject. id identifies the subject (typically a DID); other fields are the issuer's assertions about them.

Subject vs Holder

Subject is who the credential is ABOUT — the person whose degree, age, or identity is being asserted. Identified by credentialSubject.id.

Holder is who currently HOLDS the credential. Usually the subject (you hold your own driver's license). But not always — a parent could hold a child's vaccination record; an employer could hold credentials issued to its employees. In those cases the holder ≠ subject, and the holder proves authorization via Verifiable Presentations (Phase 2 material).

Optional fields you'll meet later

credentialStatus (revocation pointers — Phase 4), credentialSchema (data shape validation), refreshService (how to get a fresh credential), termsOfUse (issuer's policy constraints), evidence (proof the issuer collected to back the claim). Not in this lab's scope.

Two securing mechanisms, same proof

VCDM 2.0 separates "what's in a credential" from "how it's signed." Two separate specs handle the signing part:

Enveloping (VC-JWT)

What this lab builds

The credential JSON is wrapped INSIDE a signed envelope (a JWS). Wire format is header.payload.signature. The signature is OUTSIDE the credential — the credential lives in the payload as the vc claim.

Properties:
  • Builds on JOSE — same infrastructure as OIDC ID Tokens
  • No JSON-LD processing required to verify
  • Standardized in Securing VCs with JOSE and COSE (W3C)
  • Used by SD-JWT VC, OpenID4VC, EUDI Wallet (JSON path)

Embedded (Data Integrity)

Lab covers in Lesson 2 only

The credential JSON has a proof field added INSIDE it. Signature computed over a canonicalized form of the credential (minus the proof field). Verify by canonicalizing the same way and checking the signature.

Properties:
  • Credential remains plain JSON-LD; no unwrapping needed to read
  • Supports multiple proofs natively (multi-issuer, key rotation)
  • Requires JSON-LD canonicalization (URDNA2015)
  • Used by Sphereon, walt.id (older), some linked-data deployments

Both produce a valid VCDM 2.0 credential. They're not interchangeable on the wire — a VC-JWT and an embedded-proof VC look completely different — but they both convey the same trust claim: "the issuer signed this credential." The choice depends on the ecosystem you're integrating with.

What @context actually does

@context is a JSON-LD construct. JSON-LD ("JSON for Linked Data") gives JSON documents global, unambiguous meaning by mapping short field names to full IRIs (URLs).

The W3C VC v2 context (https://www.w3.org/ns/credentials/v2) defines what every standard VC field means in terms of RDF triples. With it, a credential is interpretable not just as "a JSON object" but as a graph of semantic facts — a JSON-LD processor can expand the credential into its full IRI form.

For VC-JWT processing, you almost never need to do that expansion

The verifier reads the credential as plain JSON, checks the standard fields (issuer, credentialSubject, etc.), and trusts that the context field's presence indicates VCDM compliance. JSON-LD machinery matters only when:

  • A verifier is performing Data Integrity verification (which canonicalizes the credential as RDF)
  • A system is doing semantic-web-style reasoning over credentials
  • A credential uses extension types (custom claim vocabularies) that need resolving

Practical takeaway

Include @context because the spec mandates it and verifiers may reject credentials without it. Don't worry about the JSON-LD machinery at the byte level until you meet Data Integrity proofs or selective disclosure in Phase 2.

What it looks like when expanded

Just for visceral effect — this is what a JSON-LD processor sees:

// Compact form (what's in the credential):
{
  "@context": ["https://www.w3.org/ns/credentials/v2"],
  "issuer":   "did:example:university",
  "credentialSubject": { "id": "did:example:alice", "name": "Alice" }
}

// Expanded form (after JSON-LD processing — what an RDF engine sees):
{
  "https://www.w3.org/2018/credentials#issuer": [
    { "@id": "did:example:university" }
  ],
  "https://www.w3.org/2018/credentials#credentialSubject": [{
    "@id": "did:example:alice",
    "http://schema.org/name": [ { "@value": "Alice" } ]
  }]
}

You don't need to write code that does this expansion for VC-JWT. But you can see why the linked-data folks like it: every field maps to a globally-unique IRI, so credentials from different vocabularies can be mixed without naming collisions.

📑 VC → VC-JWT mapping

How signCredentialAsVcJwt turns a VC JSON object into a JWT payload. The JWT carries both the original credential (under vc) AND the standard JWT claims (iss, sub, nbf, exp, jti) — duplication is intentional so plain-JWT verifiers can process expiry and issuer without understanding VCs.

VC (input)

credential

{
  "@context": [
    "https://www.w3.org/ns/credentials/v2"
  ],
  "id": "urn:uuid:abc...",
  "type": [
    "VerifiableCredential",
    "UniversityDegreeCredential"
  ],
  "issuer": "did:example:university",
  "validFrom":  "2026-09-01T00:00:00Z",
  "validUntil": "2031-09-01T00:00:00Z",
  "credentialSubject": {
    "id": "did:example:alice",
    "degreeType": "BachelorDegree",
    "name": "Alice Doe"
  }
}
VC-JWT payload

JWT payload (signed)

{
  "iss": "did:example:university",
  "sub": "did:example:alice",
  "jti": "urn:uuid:abc...",
  "nbf": 1788307200,    // unix sec of validFrom
  "exp": 1946073600,    // unix sec of validUntil
  "vc":  <the entire credential above>
}

The field map at a glance

credential.issuer → payload.iss
credential.credentialSubject.id → payload.sub
credential.id → payload.jti
credential.validFrom → unix sec → payload.nbf
credential.validUntil → unix sec → payload.exp
credential → payload.vc (whole object)

The two date conversions are the only non-trivial step. validFrom is an ISO 8601 string in the VC; nbf is a Unix-seconds integer in the JWT. Use Math.floor(Date.parse(...) / 1000).

🪪 What gets signed: enveloping vs embedded

Same credential, two different ways of attaching a signature. The wire bytes look totally different; the trust property is the same.

VC-JWT (enveloping)

Signature wraps the credential

eyJhbGciOiJFUzI1NiJ9.eyJpc3MiOi4uLi4uLnZjOnsuLi59fQ.MEUCIQ...sig

      ▲ JWS header   ▲ payload contains
                       the credential
                       inside the "vc" claim   ▲ signature

Verifier parses the JWS, extracts payload.vc as the credential, checks the signature over the encoded payload bytes. No JSON-LD processing needed.

Data Integrity (embedded)

Signature lives inside the credential

{
  "@context": [...],
  "issuer":   "did:example:university",
  "credentialSubject": {...},
  "proof": {
    "type":               "DataIntegrityProof",
    "cryptosuite":        "eddsa-rdfc-2022",
    "verificationMethod": "did:example:...#key-1",
    "proofValue":         "z3MvSi...."
  }
}

Verifier canonicalizes the credential (URDNA2015 / RDFC) MINUS the proof.proofValue, hashes, then verifies proofValue against that hash. Requires a JSON-LD processor.

Self-check & further reading

Self-check

Try to answer before clicking "Show answer".

A VC-JWT carries the credential twice — once mapped into JWT claims (iss, sub, nbf, exp) and once verbatim under the vc claim. Why the duplication?

It's a deliberate compromise. The JWT-level claims let plain-JWT verifiers (libraries that don't know what a VC is) still process issuer matching and expiry — they read iss and exp like any other JWT. The vc claim preserves the original credential JSON for VC-aware code that wants the full structure (extra type values, custom subject fields, etc.). Without the duplication you'd have to choose one consumer or the other.

In OIDC, the OP must be online during every login. In VC, when does the issuer need to be online — and when does it not?

The issuer needs to be online ONLY at issuance — when minting and signing the credential for the holder. After that, the verifier checks the credential's signature using just the issuer's public key (typically fetched from the issuer's DID Document or a JWKS endpoint, both of which can be cached). The issuer is never asked to authorize a presentation. This is what makes mDL work offline at a bar: the verifier already has the DMV's public key cached.

Subject and holder are usually the same person but can differ. Give an example where they differ, and how the holder proves authorization without being the subject.

A parent holds a child's vaccination record; the child is the subject (credentialSubject.id = child's DID), but the parent is the holder presenting it to a school nurse. In modern profiles, the holder authorizes via a separate signed presentation (Verifiable Presentation), where they prove control of an authorization relationship to the subject's DID. This is "key binding" / "holder binding" territory — Phase 2.

A VC is signed by the issuer's private key. The verifier eventually needs the corresponding public key. How does the verifier find it?

Through the issuer field, which is typically a DID URL (did:example:university). The verifier resolves that DID to a DID Document (Phase 1 Item 04 — DID Resolution), then reads the verification methods out of the document — usually JWKs. Specific DID methods give different resolution paths: did:web fetches over HTTPS, did:key decodes the key from the identifier itself, did:jwk wraps the JWK in the DID. The point: issuer is not just a label, it's a pointer to verification material.

What's the practical difference between an SD-JWT VC and a "regular" VC-JWT?

SD-JWT VC adds selective disclosure: instead of putting the claims plaintext into the vc payload, the issuer commits to claims via salted hashes and ships the underlying values as separate disclosures. The holder can later present a subset — show your age (just the age disclosure) without revealing your address. The signature still covers the hashed commitments, so the verifier knows the disclosed claims came from the original credential. Phase 2 material; built on top of VC-JWT structure.

A VC has @context: ["https://www.w3.org/ns/credentials/v2"] but you're processing it as VC-JWT. Do you need a JSON-LD library?

No. The @context field is part of the credential's data model, but VC-JWT processing only requires reading well-known fields (issuer, credentialSubject, type, etc.) by their literal names. You don't expand IRIs, don't canonicalize, don't do any RDF work. JSON-LD machinery becomes load-bearing only when you switch to Data Integrity proofs (which canonicalize the credential as RDF before signing) or when you need to reason about the credential's semantic content across vocabularies.

A VC-JWT carries the issuer identifier TWICE — once as the JWT-level iss claim and once inside vc.issuer. Why does the verifier check that the two are equal, and what attack does the check prevent?

Because the JWT-level claim and the embedded credential's claim are populated by different layers and an attacker can mismatch them. Scenario: attacker takes a real credential signed for did:example:university, wraps it in a JWT where iss is set to did:example:attacker, and signs the JWT with the attacker's key. A naive verifier that only checks iss against an expected attacker DID and the signature against the attacker's key will pass — but the embedded credential still claims to be issued by the university. The consistency check (payload.iss === payload.vc.issuer) is what stops this — when the verifier sees a mismatch, the credential is rejected regardless of which side passes the other checks. This is "iss-consistency" defense, sometimes called "split-brain credential" prevention.

A VCDM 1.x credential has @context: ["https://www.w3.org/2018/credentials/v1"]. A VCDM 2.0 credential has @context: ["https://www.w3.org/ns/credentials/v2"]. Why should a VCDM 2.0 verifier reject the 1.x credential, even though both are syntactically valid VCs?

Because the data model fields differ between versions. VCDM 1.x called the validity period issuanceDate/expirationDate; VCDM 2.0 renamed these to validFrom/validUntil. A verifier compiled for 2.0 looks for validUntil to compute expiry; given a 1.x credential, it would see neither validUntil nor validFrom and silently accept an "infinite-lifetime" credential — which is exactly what the issuer never meant. Enforcing @context[0] === "https://www.w3.org/ns/credentials/v2" as a hard check ensures the verifier and the credential agree on which version of the data model is in play.
