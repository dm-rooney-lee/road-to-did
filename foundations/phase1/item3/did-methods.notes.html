1 · The one question every method answers differently

Item 02 parsed DID syntax and read a DID Document that was handed to you. It left a sentence unexplained: “each method defines its own rule for how a DID maps to a Document.” That rule is really an answer to a single question:

Given the identifier, where does its DID Document come from — and whom must you trust for it?

The did:method:id segment is how you pick the answer. The four methods you should be able to compare line up on one axis, from “trust nothing but math” to “trust a chain”:

did:jwkdocument = f(identifier). The id is a JSON key.
did:keydocument = f(identifier). The id is a binary key.
did:webdocument hosted at an HTTPS URL the id points to.
did:ion / did:ebsidocument anchored on a ledger.
← self-contained · no network · trust the math infrastructure-backed · keys can rotate · trust a party/chain →
Two of these (did:jwk, did:key) are pure decoding — the lab implements them in full. did:web needs a network fetch, so the lab stops at deriving the URL. did:ion / did:ebsi need a chain, so they stay conceptual here. The uniform machinery that ties all four together — a resolve() that dispatches on the method name — is Item 04.

2 · did:jwk — the key as a JSON identifier

The simplest method. The whole DID Document is computed from the identifier, because the identifier is a public key: 

did:jwk:eyJjcnYiOiJQLTI1NiIsImt0eSI6IkVDIiwieCI6...
            └─ base64url( utf8( JSON of a public JWK ) )

Resolving it is two steps: base64url-decode the part after did:jwk:, then JSON.parse it back into a JWK. That JWK becomes the one verification method in a Document whose id is the DID itself.

The JWK’s use decides which relationships appear

This is the one subtlety. use is an optional JWK member (RFC 7517 §4.2 — see Phase 0 Item 02’s JWK tab) that declares the key’s intended purpose. It has two values and is frequently omitted: "sig" (a signing key), "enc" (an encryption / key-agreement key), or absent. did:jwk reads it to gate the verification relationships — the authorization layer from Item 02’s Lesson 2 — that the one key may appear under: 

use: "sig"  → authentication, assertionMethod, capabilityInvocation, capabilityDelegation
use: "enc"  → keyAgreement only
use absent  → all five

The five verification relationships, one line each

Defined by DID Core and introduced in Item 02 §5 — but the capability pair is spelled out here for the first time. Each relationship answers “what is this key allowed to be used for?”

relationshipkey family“this key may be used to…”
authenticationsigningprove you control the DID — log in / authenticate as the subject
assertionMethodsigningsign assertions — i.e. issue Verifiable Credentials (Item 01’s issuer key)
capabilityInvocationsigninginvoke an authority you hold — e.g. authorize a privileged action, including updating the DID Document itself
capabilityDelegationsigningdelegate an authority to someone else (hand a capability down the chain)
keyAgreementencryptionderive a shared secret for encryption (key exchange / ECDH) — not signing
The split lines up exactly with use: the four signing relationships ride with "sig", the lone encryption relationship (keyAgreement) with "enc", and an absent use can’t rule either out, so all five appear. The capability pair comes from the object-capability (ZCAP) model — “a signed permission you can use, or pass on”; you don’t implement that machinery here, only place the key under the right relationship.
Verbose but human-legible: one base64url decode and you can read the key type in plain words ("kty":"EC"). That readability is the trade did:jwk makes against the next method.

3 · did:key — the key as a self-describing binary blob

Same trust model as did:jwk — the key is the identifier — but the envelope is compact binary instead of JSON. Two “self-describing” layers stack inside the part after did:key:: 

did:key:z6Mke…
        │└── base58btc( <multicodec prefix> ‖ <raw public key bytes> )
        └─── multibase tag: "z" means "the rest is base58btc"

multibase + multicodec = two type tags the bytes carry themselves

layerquestion it answersdid:key’s value
multibasewhich base is the text in?z → base58btc
multicodecwhich key type are the bytes?e.g. 0xed 0x01 → Ed25519 public key

So resolving is: drop the z, base58btc-decode, read the first two bytes as the multicodec (which curve), and the remaining bytes are the raw public key. The lab supports two codecs: 

0xed 0x01  ed25519-pub  → { kty:"OKP", crv:"Ed25519" }  — a signing key
0xec 0x01  x25519-pub   → { kty:"OKP", crv:"X25519"  }  — a key-agreement key

And — just like did:jwk’s use — the curve decides the relationships. An Ed25519 key is for signing (authentication + assertionMethod + the two capability relationships); an X25519 key is only for key agreement (keyAgreement). The verification-method id follows the did:key convention that the fragment equals the whole z… string: did:key:z6Mke…#z6Mke….

The multi- family (multibase, multicodec, multihash, multiaddr) is borrowed from the content-addressing / IPFS world. “Self-describing” means a reader never needs to be told out of band how to interpret the bytes — the type tag travels with the value. You’ll meet multihash again wherever a hash has to announce its own algorithm.
Out of scope: a real did:key resolver, given an Ed25519 key, also derives a separate X25519 keyAgreement key by converting the Edwards point to Montgomery form. That curve math is not in the lab — we stop at the key the identifier directly encodes.

4 · did:web — the document as a hosted resource

Here the axis tips over. The document is not in the identifier. The identifier names a domain; the document is whatever did.json is hosted there right now. Resolving means turning the DID into a URL and fetching it — and the lab implements the first half only (the fetch is Item 04): 

did:web:example.com                 → https://example.com/.well-known/did.json
did:web:example.com:user:alice      → https://example.com/user/alice/did.json
did:web:example.com%3A3000:user:bob → https://example.com:3000/user/bob/did.json

The rules: : separates segments; the first segment is the authority; remaining segments become path components and the URL ends in did.json; with no path it’s /.well-known/did.json. A port colon is percent-encoded (%3A) so it isn’t mistaken for a separator.

What you gave up, and what you bought. Unlike did:key/did:jwk, the document can be edited or replaced by whoever controls the domain — your trust in it reduces to your trust in that domain’s DNS and TLS. In exchange you get something the self-contained methods can never have: the identifier stays fixed while the keys inside its document rotate. (More in §6.)

5 · did:ion / did:ebsi — the ledger end (concept only)

The far end of the axis. Instead of a single web server, the document — or its history of signed update operations — is anchored on a ledger, so no one domain can quietly change it.

  • did:ion — a Sidetree-based method anchoring batches of DID operations to Bitcoin, with the bulk of the data in IPFS. No permission needed to create one; the chain orders the updates.
  • did:ebsi — the EU Blockchain Services Infrastructure’s method, on a permissioned ledger run by member states. Used in EU digital-identity pilots.

The point for this item is only their place on the axis: trust roots at a chain’s consensus rather than a domain or pure math. There is no chain to read here, so the lab doesn’t implement them.

The clean split is self-contained (jwk, key) vs hosted/anchored (web, ion). The first pair trades away key rotation for zero infrastructure and an unforgeable binding; the second pair trades in a trust dependency to gain a stable identifier whose keys can change over time. That is the whole decision.
