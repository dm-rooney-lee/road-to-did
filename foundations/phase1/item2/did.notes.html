1 · The gap Item 01 left open

Item 01's verifier signature was:

verifyVcJwt(vcJwt, publicKey: KeyObject, expectations)

That publicKey arrived from nowhere. The contract called it "the issuer's public key the verifier trusts for this issuer" — and quietly assumed you already had it and already trusted it. Two unanswered questions hid in that phrase:

  • Discovery — given an issuer named did:example:123, where do you get the key bytes?
  • Binding — what makes that key authoritatively the issuer's, with no Certificate Authority vouching?

A DID answers discovery: it is a string that resolves to a DID Document, a JSON object listing the controller's public keys. The binding answer is per-method (see §7) — but in every case the controller of the DID, not a third party, governs the Document.

This item implements the parts that need no network: parsing the identifier (§2–3) and reading the Document (§4–6). The act of fetching a Document from a live DID — resolution — is Item 04.

2 · The DID and DID-URL grammar

A bare DID has exactly three parts (DID Core §3.1):

did:example:123456789abcdefghi
schemeAlways the literal did. Like https in a URL.
method1*( a-z / 0-9 ) — lowercase only. Names the ruleset for how this DID resolves and who may change it.
method-specific-idDefined by the method. May contain further : separators (e.g. did:web:example.com:user:alice). Allowed chars: A-Z a-z 0-9 . - _ and %-encoding.

A DID URL layers path, query, and fragment on top of the bare DID (§3.2)

did:example:123/a/b?x=1#key-1 
did-url = did path-abempty [ "?" query ] [ "#" fragment ]
pathBegins at the first /, runs until ? or # or end. Returned with its leading /.
queryBegins at ?, runs until # or end. Returned without the ?.
fragmentBegins at the first #, runs to the end. Returned without the #.
Order is fixed: path → query → fragment. So the first # starts the fragment even if a # also appears later inside it, and the first ? after the path starts the query. The parser in §3 enforces exactly these boundaries.

4 · The DID Document

Resolving a DID yields a JSON object. Annotated:

{
  // JSON-LD context, like a VC's @context
  "@context": ["https://www.w3.org/ns/did/v1"],

  // the DID this document describes — its own name
  "id": "did:example:123",

  // the CATALOGUE of keys: each is a full key with material
  "verificationMethod": [{
    "id": "did:example:123#key-1",   // a DID URL: DID + fragment
    "type": "JsonWebKey2020",
    "controller": "did:example:123",
    "publicKeyJwk": { "kty": "EC", "crv": "P-256", "x": "…", "y": "…" }
  }],

  // AUTHORIZATION: which keys may be used for which purpose
  "authentication":  ["did:example:123#key-1"],   // reference string
  "assertionMethod": ["did:example:123#key-1"]     // the VC-signing purpose
}

buildDidDocument (Section 2) assembles this: it passes verificationMethod through, and for each relationship the caller asks for, emits an array of reference strings pointing back into the catalogue (define a key once, authorize it many times).

5 · Verification methods vs verification relationships

The single most important structural idea in the Document. Two separate concerns:

verificationMethod "Here is a key." The catalogue. id + type + controller + key material.
relationships
authentication, assertionMethod, keyAgreement, capabilityInvocation, capabilityDelegation		 "This key may be used for this purpose." An authorization layer over the catalogue.

Each relationship entry is one of two forms:

"assertionMethod": [
  "did:example:123#key-1",          // REFERENCE → defined under verificationMethod
  { "id": "did:example:123#key-9",  // EMBEDDED → defined right here, used only for this purpose
    "type": "JsonWebKey2020", "controller": "…", "publicKeyJwk": {…} }
]
Why this is a security boundary, not bookkeeping. A VC issuer signs credentials with an assertionMethod key. If a credential is signed by a key the issuer's Document lists only under keyAgreement (key for encryption, not assertions), a correct verifier rejects it — the issuer never authorized that key to make claims. Finding the key (§6) and checking which relationship it sits under are two different steps. Item 01's verifyVcJwt skipped the second because it was handed a single trusted key; a real verifier does not get that luxury.

6 · Dereferencing a verification method

A VC-JWT issued under a DID carries a key id (the JWS kid) — a DID URL like did:example:123#key-1. To turn that into key bytes, dereferenceVerificationMethod (Section 3) runs:

  1. Scope check. Split the reference into its bare DID and fragment (using your §1 parser). If the bare DID ≠ the Document's id, this Document cannot speak for it → null. This is the load-bearing check: accepting a key whose DID doesn't match the document is how you'd trust the wrong issuer.
  2. Catalogue lookup. Find a verificationMethod entry whose id equals the full reference → return it.
  3. Embedded lookup. Otherwise scan each relationship array for an embedded object (not a string) whose id matches → return it.
  4. No match anywhere → null.
String entries in a relationship are resolved by step 2 (they point into the catalogue), not step 3. Step 3 only matches inline objects. The two forms from §5 are exactly why the search has two places to look.

Then the loop closes: read publicKeyJwk off the returned method, import it to a KeyObject, and hand it to the very verifyVcJwt you wrote in Item 01.

7 · Why a method segment exists at all

The method in did:method:id selects the rule for two things: how the DID maps to its Document, and who is allowed to change it. That choice is the root-of-trust knob.

did:keyDocument is derived deterministically from the key in the id itself. No registry, no network. Self-certifying; cannot rotate keys.
did:webDocument lives at a well-known HTTPS URL under a domain. Trust = trust the domain/TLS. Most practical to deploy.
did:jwkA single JWK wrapped as a DID. Like did:key but JWK-native.
did:ion / did:ebsiDocument state anchored on a ledger. Trust = trust the chain. Supports rotation and history.

Same identifier shape, four different answers to "what makes this key authoritative." Item 03 compares these head-to-head; Item 04 implements resolution for the network-free ones.

Contrast with X.509 (the eIDAS route, Item 05): there a Certificate Authority signs a name→key binding and everyone trusts the CA. DIDs move the binding's authority to the identifier's controller. Whether that is better is exactly the trade-off Item 05 asks you to weigh.
