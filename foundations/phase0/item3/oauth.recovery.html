Step 1AS overload at /authorize

Failure: client redirects user to the auth server's /authorize endpoint. AS is under load — returns HTTP 5xx, error=server_error, or just times out. User sees a broken auth screen or a spinning page.

Failure topology

Clientbrowser
GET /authorize?… → 500 / timeout
Auth Serveroverloaded

Solutions

1️⃣ Client backoff + retry client

Client catches the failure, waits with jittered exponential backoff, retries 2–3 times before surfacing an error.
t=0GET /authorize500 +150msretry 1500 +480msretry 2500 +1.6sretry 3200
✓ No server changes needed. ✓ Smooths transient blips invisibly.
✗ Without jitter, simultaneous clients dogpile on the AS once it recovers.

2️⃣ Edge rate limiting infra

API gateway / Envoy in front of AS enforces per-client (or per-IP) rate limits. AS itself never sees overload traffic — gateway returns 429 first.
Client
/authorize→
Gatewayrate limit
passes→
AS
✓ Protects AS from abusive clients. ✓ Fast rejection (50ms 429) instead of slow 5xx.
✗ Doesn't help if a legit single client suddenly spikes (gateway throttles them).

3️⃣ Server-side load shedding server

When AS detects it's at capacity (CPU > 80%, queue > N), it returns 503 Retry-After: 5 immediately rather than queuing requests until timeout.
t=0/authorize → AS503 R-A:5 +5sclient retries200
✓ AS recovers faster (sheds load before melting). ✓ Clients respect Retry-After if implemented.
✗ Requires AS to know its own capacity in real time.
Combinable? All three stack. Different targets:
Client backoff = recover from any 5xx.
Gateway rate limit = stop abusive traffic at the edge.
Server load shedding = AS's last line of defense when even legit traffic exceeds capacity.
Typical production setup uses all three simultaneously.

Step 3Your /callback page overloaded

Failure: User authenticated successfully. AS issued a code. Browser is redirected to https://wallet.example.com/callback?code=…. But your callback page returns 5xx — your web tier is overloaded. The code expires in 60 seconds. User stuck. This is the most brutal failure mode because there's no recovery from the client side: the code is dying in real time.

1️⃣ Static /callback from CDN architecture

Make /callback a static HTML page served from CDN/edge. The page does the token exchange asynchronously via fetch() to a separate backend endpoint. The static page is virtually impossible to overload.

✓ /callback can never overload. ✓ Decouples render from backend load.
✗ Token exchange API can still overload — but that hits step 5's playbook, which has more options.

2️⃣ Highest-priority pool for /callback infra

Keep /callback on its own LB pool, separate from the rest of your web tier. Reserve capacity for it. Other endpoints can degrade first.
✓ Cheaper than splitting architecture. ✓ /callback isolated from non-OAuth load spikes.
✗ Still has finite capacity — a true spike (e.g. mass-onboarding event) can saturate.
Combinable? Yes — use option 1 (static + async) as the primary architecture; option 2's isolated pool now applies to the token-exchange API, not the static page. Defense in depth.

Step 5AS overload at /token (5xx / 429)

Failure: Client sends POST /token with code + verifier. AS responds with HTTP 503, 429, or times out. The code was not consumed — AS rejected before redemption logic ran.

Failure topology

Client
POST /token → 503 / 429
ASoverloaded

Solutions

1️⃣ Client backoff + retry client

Same shape as step 1. The code is still valid; same code + verifier can be retried.
t=0POST /token429 +200msretry 1429 +600msretry 2200
✓ Code remains valid for the 60s window — usually enough.
✗ Must NOT retry on invalid_grant — that means the code is dead.

2️⃣ Aggressive timeout (5s) client

Don't wait 30s for a slow response. Abort at 5s and treat as ambiguous failure → restart entire flow.
✓ Fails fast. ✓ Prevents resource pile-up on client side.
✗ Aborts when AS would have succeeded at 6s. ✗ Restarting flow costs the user a re-consent.

3️⃣ Honor Retry-After client

If AS returns Retry-After: N header (with 429 or 503), wait exactly N seconds before next retry — don't dogpile.
✓ Coordinates with AS recovery. ✓ Spec-compliant.
✗ Most clients ignore this header — needs explicit handling.

4️⃣ Circuit breaker client

If /token fails N times in M seconds, stop sending requests for a cooldown period. Show "service unavailable" to incoming users.
✓ Prevents client-side dogpile on a degraded AS. ✓ Speeds AS recovery.
✗ Innocent users hit the breaker; need careful tuning.
Combinable? All four stack. Usually layered as: per-attempt timeout + across-attempt backoff with Retry-After + global circuit breaker. Standard library combo (most HTTP retry libraries do all three).

Step 5⚡ Lost response problem most subtle

Failure: Client sends POST /token. AS receives it, redeems the code, mints tokens, starts writing the response — then the TCP connection dies (load balancer scaled out, network blip, AS instance restarted). Client never sees the response. Client retries with same code + verifier. AS rejects: invalid_grant (code already redeemed). Tokens were issued but lost forever.

Why traffic-driven? At low load, TCP connections are stable. At high load, LBs scale out, AS instances cycle, connection pools exhaust → mid-request connection failures spike. Becomes a measurable percentage of token exchanges.

Solutions (four mutually-exclusive server patterns + one client-side defense)

A. Client-side: ambiguous-failure detection client

Distinguish "got a 5xx response" (safe to retry) from "request aborted with no response" (code may be consumed). On ambiguous failure, restart the flow from step 0 — accept the lost code.
try {
  const res = await fetch('/token', {…, signal: timeout(5000)});
  if (res.status >= 500) RETRY_SAFE;        // try again
  if (res.status === 400 && res.body.error === 'invalid_grant')
                                  RESTART;  // code dead
} catch (e) {
  if (e.name === 'AbortError') RESTART;     // ambiguous → assume dead
  if (e.name === 'NetworkError') RESTART;
}
✓ Pure client change. ✓ Works regardless of AS implementation.
✗ User has to re-consent. ✗ Slightly inflated re-auth rate.

B. AS-side: distributed lock on code server

First redemption acquires a Redis lock keyed by code (TTL 30s). Concurrent retry blocks on the lock, then re-reads the result from storage. The "lost response" client's retry now succeeds with the cached tokens.
AS-1has lock
writes tokens→
Rediscode → tokens
retry blocks↓
AS-2waiting
✓ Transparent to client. ✓ User keeps their session.
✗ Adds Redis hot key per code. ✗ Lock TTL tuning matters.

C. AS-side: idempotency window server

When AS redeems a code, it stores the response alongside the consumed-marker for ~30s. On retry within that window, return the cached response instead of invalid_grant.
// In AS code-redemption logic
if (code.status === 'redeemed' &&
    code.redeemed_at > now() - 30s) {
    return code.cached_response;   // ← idempotent
}
if (code.status === 'redeemed') {
    return invalid_grant;          // window expired
}
// ...normal redemption...
✓ No coordination needed (writes serialized by code-store). ✓ Simpler than option B.
✗ Storing response bytes inflates code-store size. ✗ Security gotcha: only return cached response to same client_id + code_verifier.

D. Saga / event-sourced redemption server

Treat redemption as an ordered sequence of events: code.locked → tokens.minted → tokens.delivered. On retry, AS replays from the last completed step. Heavy machinery; used in microservice estates where multiple downstream services participate.
✓ Survives multi-step failures, not just lost responses. ✓ Audit trail built in.
✗ Significant complexity. ✗ Most teams shouldn't reach for this first.
Combinability matrix (lost-response options only):
A (client)B (lock)C (idempotency)D (saga)

Recommended: A (always — costs nothing) + one of B / C / D depending on infrastructure. B and C are functionally similar; D is overkill unless you have cross-service redemption.

Picking B vs. C: B handles concurrent retries cleanly but adds a Redis lock per code. C is simpler but needs careful security around "who's allowed to read the cached response."

post-flowRefresh stampede (synchronized token expiry)

Failure: Morning login peak: 10,000 users sign in within a 5-minute window. One hour later, all 10,000 access tokens expire within the same 5-minute window. All clients try to refresh simultaneously. AS gets a synchronized 10,000-request spike at /token (refresh grant). Subset of refreshes fail → fall back to full reauth → spike at /authorize too.

Failure topology

10,000
clients
all refresh
at same minute →
ASspike at /token

Solutions

1️⃣ Stagger token lifetimes server

Instead of expires_in: 3600 (exactly 60 min), use 3300 + random(0..600) — 55–65 min. Same users now refresh spread over 10 min instead of clustered at 60 min.
✓ Smooths peak by ~10×. ✓ Trivial to implement (one line at token mint).
✗ Doesn't help if all users log in in the same minute (which can still synchronize).

2️⃣ Client-side stale-while-revalidate client

Client doesn't proactively refresh on expiry. Only refreshes when an API call returns 401 (token rejected by resource server). Most users don't hit 401 at exactly t=60min — they hit it whenever they next make an API call, which is naturally spread out.
✓ Eliminates synchronized refresh entirely. ✓ Saves wasted refreshes for idle users.
✗ First API call after expiry pays a refresh+retry latency penalty.

3️⃣ Server-side circuit breaker / load shedding server

When /token hits capacity, AS returns 503 Retry-After: X to refresh requests preferentially (over new-auth requests). Some users see brief delay; the AS doesn't collapse.
✓ AS survives genuine spikes. ✓ Prioritizes new logins (more user-visible) over refreshes.
✗ Requires client respect for Retry-After. ✗ Some API calls fail in the window.

4️⃣ Longer token lifetime + revocation architecture

Make access tokens last hours (8h, 12h), reducing refresh frequency. Pair with a revocation list / introspection cache so compromised tokens can still be invalidated quickly.
✓ Drastically reduces refresh load. ✓ Better user experience (fewer "session expired" surprises).
✗ Longer-lived tokens = larger blast radius if stolen. ✗ Revocation complexity.
Combinable? All four stack.
Realistic production setup: stagger + SWR as defaults; circuit breaker as safety net; longer lifetimes as a scaling-cost optimization once the first two are in place. Each addresses a different failure mode — stacking gives compound mitigation.

Read this matrix as:

  • Each column = recovery stack for one failure mode. Multiple layers cooperate.
  • Each row = where you'd implement that layer in your infrastructure.
  • Step 5 lost response is the only column with mutually-exclusive AS-side options — pick one of B/C/D, don't stack them.
  • Client-side defenses (top row) are always free to add — they don't conflict with anything.

Order of investment

If you're starting from scratch and prioritizing, this is roughly the order to add things by cost-vs-benefit:

  1. Client backoff + timeout (covers ~80% of transient blips, almost free)
  2. Static /callback page (covers the worst failure mode at low effort)
  3. Edge rate limiting (protects AS from one bad client melting everyone)
  4. Stagger token lifetimes (one-line change, big peak-smoothing effect)
  5. Idempotency window OR distributed lock at AS (fixes the lost-response trap)
  6. Server-side load shedding + circuit breakers
  7. State-store sharding + scaling
  8. Saga/event-sourced redemption (only if downstream complexity warrants)
