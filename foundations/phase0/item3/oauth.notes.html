Background — read first

Three things to know before the walkthrough: what PKCE is, who's who, and what each token means.

PKCE (pronounced "pixy") = Proof Key for Code Exchange — RFC 7636. A small extension to OAuth 2.0 that solves one specific problem: authorization-code interception. An attacker who steals the code from the browser layer (malicious mobile app, deep-link hijack, browser history exfil) cannot redeem it without a matching secret the client held back — the code_verifier.

Why isn't TLS alone enough? TLS encrypts the network link between client and AS. But the code arrives via a browser redirect URL — it's processed by the user-agent (browser address bar, browser history, OS deep-link routing, Referer headers from the callback page). None of that is "in transit" to the AS; it's all post-decryption, on the user's device. TLS doesn't reach there. PKCE adds a second secret that travels only on the back-channel TLS link, never through the user-agent layer.

A third parameter, code_challenge_method, tells the AS which transform produced the challenge. Use S256. The spec also defines plain (challenge = verifier, no hashing) — but that defeats PKCE entirely and is forbidden by every modern profile (OAuth 2.1, OpenID4VC, FAPI).

How the AS uses them

In step 1 (front-channel) the AS stores the code_challenge alongside the session. In step 5 (back-channel) the client sends the code_verifier. The AS computes SHA-256(submitted_verifier) and compares to the stored challenge. Match → mint tokens. Mismatch → reject.

The "Try the attack" section at the bottom of this page lets you watch the rejection happen byte-by-byte. The PKCE playground tab in the live-state panel lets you experiment with the SHA-256 transform yourself.

OAuth defines four actors. Every spec downstream (OIDC, OpenID4VC) uses these labels — memorize them.

The user (you)

Client

The app requesting access (wallet, mobile app, SPA)

Authorization Server

Issues tokens. Hosts /authorize and /token. Examples: Google, Auth0, your in-house AS

OAuth uses several token types with very different lifetimes and purposes. Don't conflate them.

Authorization code

~60 seconds, single-use
Opaque random string the AS mints in step 3, after the user authenticates and consents. Defined by RFC 6749 §1.3.1; the response format is in §4.1.2.
Sent: front-channel URL (step 4 callback)
Format: implementation-defined. The spec just says "opaque to the client, single-use, short-lived." Common in practice: 16–32 cryptographically random bytes, base64url-encoded. Could also be a UUID, an internal session key, an HMAC-signed token — as long as the AS can map it back to the session it stored in step 1.
Why a code (not a token) is returned here: the access/refresh tokens are long-lived and powerful. If they came back in the step-4 redirect URL, they'd hit browser history, server logs, Referer headers — same exposure problem PKCE addresses for the code. By issuing a short-lived single-use code first, the AS keeps the actual tokens off the front-channel entirely; they're issued only on the back-channel response in step 6.

Access token

Minutes–hours
The actual permission. Carried as Authorization: Bearer <token> to the resource server.
Sent: back-channel /token response

Refresh token

Days–months
Long-lived re-grant material. Trade it at /token for a fresh access token without user reauth.
Sent: back-channel only

ID token (OIDC only)

Minutes
A JWT (Item 02!) carrying identity claims. Only appears when scope includes openid.
Issued alongside access token

In OpenID4VC, the access token buys you a verifiable credential at the credential endpoint — same flow shape, different payload at the end.

Self-check & further reading

Self-check

Try to answer before clicking "Show answer".

What does PKCE protect against, and why isn't TLS (HTTPS) alone enough?

Authorization-code interception. TLS protects the link between client and AS, but the redirect to redirect_uri exposes the code to the user-agent layer: browser history, OS deep-link routing, server access logs, Referer headers. A malicious app or a network observer on the user's device can grab the code. PKCE binds redemption to a verifier that never travels on that channel — the stolen code is useless without it.

code_verifier and code_challenge are mathematically related. Which is secret, and why?

The verifier is secret (kept in client memory). The challenge is public (sent in the authorization URL). SHA-256 is one-way: given the challenge, you can't recover the verifier. So publishing the challenge in step 2 is safe, and only the original client (the one holding the verifier) can redeem the code in step 5.

Why is state validated by the client, not the auth server?

Because state defends against login CSRF — an attacker tricking the client into accepting a code from an attacker-initiated flow. The auth server doesn't care; it just echoes the value back. The client is the one that needs to confirm "this callback corresponds to a flow I started." Only the client knows what value it generated.

What's the wire format for the auth request query string AND the token request body? Why isn't either JSON?

Both use application/x-www-form-urlencoded — the same key=value&key=value encoding. Auth request: in the URL query string. Token request: in the POST body. Not JSON because OAuth predates JSON's dominance, and the form-encoded format is what HTML forms produce — easy to debug, easy to log, no parser dependency.

In the OpenID4VC mapping, who plays each of the four OAuth roles?

Resource Owner = the credential subject (the user). Client = the wallet. Authorization Server = the credential issuer's auth endpoint. Resource Server = the credential endpoint (which hands back the verifiable credential instead of API resources).

If code_challenge_method=plain is in the spec, why should you reject it in production code?

With plain, the challenge equals the verifier — no hashing. An attacker who intercepts step 2 sees both the challenge and a directly-usable verifier. PKCE is defeated. Modern profiles (OAuth 2.1, OpenID4VC, OIDC FAPI) mandate S256.
