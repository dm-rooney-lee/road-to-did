Background — read first

Four things to understand: the family of specs, the compact JWS structure, the algorithm registry, and the key serialization format.

Five related specs from the IETF JOSE working group, all published in 2015 (RFC 7515–7519). They form a family — most JWTs you'll meet use JWS + JWA + JWK; JWE is rare in identity work.

Term Spec What it is
JWT RFC 7519 A JSON claims set packaged inside either a JWS or a JWE. The "outer" concept everyone talks about.
JWS RFC 7515 Signed payload. Three parts: header.payload.signature. Almost every JWT you'll meet in VC/DID work is a JWS.
JWE RFC 7516 Encrypted payload. Five parts. Rare in identity protocols.
JWA RFC 7518 Algorithm registry. Maps short names → crypto primitives: ES256, RS256, EdDSA, HS256, …
JWK RFC 7517 JSON serialization of a key (public or private).

In conversation: "JWT" is shorthand for "compact JWS containing a JSON claims set." Strictly, the JWT is the claims; the JWS is the envelope. Don't get hung up on it — but know that "verifying a JWT" really means "verifying the JWS that wraps it."

Where you'll meet each in DID/VC

  • JWS — every VC-JWT, every SD-JWT, every OpenID4VC token. Constant exposure.
  • JWK — published at /.well-known/jwks.json, embedded in did:jwk identifiers, inside did:web DID documents. Constant exposure.
  • JWA — every alg value (ES256, EdDSA) you ever type. Implicit, but everywhere.
  • JWT — the term in casual conversation; usually means JWS-with-JSON.
  • JWE — almost never. Credential confidentiality is handled by TLS + selective disclosure, not by encrypting the credential itself.

The compact serialization

Three URL-safe segments joined by literal dots:

header base64url(JSON)
.
payload base64url(JSON)
.
signature base64url(bytes)

What's actually signed

The signing input is the ASCII string base64url(header) + "." + base64url(payload) — exactly that, including the literal dot, before the third segment exists. The signature is over those bytes, NOT over the raw JSON.

Why sign the encoded form? JSON has ambiguity: whitespace, key order, number formatting. Different JSON serializers produce different bytes. By signing the base64url-of-JSON, both parties agree on exact bytes without arguing about whitespace.

base64url

Standard base64 uses +, /, and = padding. None of those are URL-safe (+ becomes space in query strings, / is a path separator, = is reserved). base64url swaps the alphabet (+ → -, / → _) and drops = padding. Node has it built in: buf.toString('base64url') and Buffer.from(s, 'base64url').

Algorithm registry (JWA)

Each alg value in a JWS header is a short name from this registry. JWA itself is just the table — it doesn't define new crypto.

NameCryptoWhere
ES256 ECDSA P-256 + SHA-256 JWT/VC default. The algorithm you built in Item 01.
EdDSA Ed25519 Modern OpenID4VC, did:key, newer profiles.
RS256 RSA-2048+ + SHA-256 Legacy OIDC (Google OAuth, Auth0 defaults).
HS256 HMAC-SHA256 (symmetric) Session tokens with a shared secret. Never for VC.
none no signature Attack vector — see the simulator below.

ECDSA signature format — DER vs JOSE raw

This one bites everybody once.

  • Node's default crypto.sign('sha256', msg, ecKey) returns a DER-encoded ECDSA signature: 70–72 bytes of ASN.1 with length prefixes.
  • JWS requires raw R∥S concatenation (RFC 7518 §3.4): for P-256, exactly 64 bytes.

To switch Node into JOSE form, pass dsaEncoding: 'ieee-p1363' to sign/verify. Forget it and your token will look fine in jwt.io but real verifiers (browsers, other-language libraries) will reject the signature with no obvious clue why.

JSON Web Key — keys as JSON

A serialization format for keys (public or private). The same P-256 key from Item 01, written as JSON:

{
  "kty": "EC",
  "crv": "P-256",
  "x": "f83OJ3D2xF1Bg8vub9tLe1gHMzV76e8Tus9uPHvRVEU",
  "y": "x_FEzRu9m36HLN_tue659LNpXW6pCyStikYjKIWI5a0"
}

kty

Key type
EC (elliptic curve), RSA, or OKP (octet key pair — used for Ed25519).

crv

Curve name (EC/OKP only)
P-256, P-384, Ed25519, etc.

x, y

Curve point coordinates
base64url-encoded big-endian bytes. For P-256, each is 32 bytes → 43 base64url characters.

d

Private key — for private JWKs only
Also base64url. If you see d in a public JWK, you've leaked a private key.

JWK Set (JWKS)

A bundle of multiple keys, conventionally published at /.well-known/jwks.json:

{
  "keys": [
    { "kid": "key-2024", "kty": "EC", "crv": "P-256", "x": "…", "y": "…" },
    { "kid": "key-2025", "kty": "EC", "crv": "P-256", "x": "…", "y": "…" }
  ]
}

Verifiers fetch the issuer's JWKS, pick the right key by kid (key ID, usually copied from the JWT header), and verify.

🦹 The alg: none attack

In 2015 several mainstream JWT libraries were found to trust the alg field in the (attacker-controlled) header and dispatch accordingly:

  • alg: 'ES256' → run ECDSA verify
  • alg: 'none' → return true, skip verification entirely

An attacker crafted {"alg":"none"} with an empty signature, the library returned "valid", and the payload was trusted. The fix is a single discipline: the verifier knows what algorithm it expects. Reject anything else.

Self-check & further reading

Self-check

Try to answer before clicking "Show answer".

A "JWT" is technically two things stacked. What wraps what?

The JWT is the JSON claims set (the payload). It's wrapped in a JWS (signed envelope) — or much more rarely a JWE (encrypted envelope). "JWT" in casual usage = "JWS containing a JSON claims set."

Why does the verifier compute the signature over base64url(header) + "." + base64url(payload) instead of over the raw JSON?

Because JSON has ambiguity — whitespace, key order, number formatting — and different serializers produce different bytes for "the same" object. Signing the base64url-of-JSON guarantees both parties agree on the exact byte sequence to verify against. The encoded form is canonical; the JSON form isn't.

What attack does {"alg": "none"} enable, and what one rule kills it?

The attack: an attacker sends a token with alg:none and an empty signature. A naïve verifier that uses header.alg to dispatch the verification function will pick the no-op verifier and return "valid". The one rule that kills it: the verifier enforces an expected algorithm, regardless of what the header claims. Use header.alg only to match against your expectation, never to select the verifier.

What does exp: 1758000000 mean — and what bug do you create if you confuse it with milliseconds?

exp is in Unix seconds. 1,758,000,000 seconds since 1970 = around late 2025. If you accidentally treat it as milliseconds, the same value lands in the year 57735 — your token effectively never expires. Always use Math.floor(Date.now() / 1000), not Date.now().

Given a JWK with kty: "EC", crv: "P-256", x, y — how does that JSON correspond to the public key bytes of an ECDSA P-256 keypair you generated in Item 01?

The keypair has a public point (x, y) on the P-256 curve. Each coordinate is a 32-byte big-endian integer (because P-256 is a 256-bit curve). The JWK stores those bytes base64url-encoded — so x and y are each 43 characters long. Decode them and you get back the raw 32-byte coordinates that, together, define the public point.

Two JWTs signed with the same ES256 key over the same payload — will their signature segments be byte-equal? Why or why not?

No. ECDSA requires a fresh random nonce k for every signature. The signature embeds k, so different runs produce different signatures even for identical inputs. (Compare with EdDSA, which derives k deterministically and produces byte-identical signatures for identical inputs.) See Item 01's Lesson 1.

If you signed a JWT with Node's default sign('sha256', ..., key) and a browser verifier rejected it, what's the most likely cause?

DER vs JOSE format. Node's default is DER-encoded ECDSA signatures (70–72 bytes of ASN.1). JWS requires raw R∥S concatenation (64 bytes for P-256). Pass dsaEncoding: 'ieee-p1363' to sign to get the JOSE format. Symptom is exactly this: token looks fine in jwt.io, fails in real verifiers.
