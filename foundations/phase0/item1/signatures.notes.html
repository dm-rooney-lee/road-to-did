Background — read first

Three things to understand: the two-key idea, why we always hash before signing, and the three algorithm families you'll meet.

The two-key idea

Every party has a keypair: two values produced together by the same math, used in opposite directions.

🔒 Private key

Kept secret. Never leaves the signer's machine.
Used to sign messages (or decrypt messages encrypted to you).

👁 Public key

Share freely. Travels in DIDs, JWKs, certificates.
Used to verify signatures (or encrypt messages to the holder).

For DID/VC work, you only care about signing. Encryption is a different problem solved by different protocols.

What a signature proves

A small blob (~64 bytes for modern algorithms) that proves two things together:

Authenticity

The signer holds the private key. Whoever can produce a valid signature must have access to the secret key.

Integrity

The message has not been altered since signing. A single-byte change makes verification return false.

What a signature does NOT prove

Confidentiality

The message is still readable. Signing doesn't encrypt.

Freshness

An attacker could replay an old signed message. You need timestamps or nonces for that.

Real-world identity

Only that the signer holds that specific key. Mapping keys to humans/orgs is the trust problem — solved later by trust registries, x509 chains, DID resolution.

Why we sign the hash, not the message

Signing primitives are slow and operate on fixed-size inputs. A hash function turns any-size input into a fixed-size fingerprint (32 bytes for SHA-256). The universal pattern:

Input message
any size
→
SHA-256 32-byte digest
fixed size
→
Sign signature
fixed size

This is why every JWT signs base64(header) + "." + base64(payload) as a hash, not the raw JSON. The encoded form is also deterministic; different JSON serializers wouldn't agree on whitespace or key order, but they agree on encoded bytes.

SHA-256 properties

Deterministic

Same input → same output, always. SHA-256 has no randomness.

Fixed-size output

Always 32 bytes (256 bits), regardless of input size.

One-way

Given a hash, you can't recover the input. Brute force is infeasible (2256 possibilities).

Collision-resistant

Practically impossible to find two inputs that hash to the same output.

⚠️ NOT for passwords

SHA-256 is for fingerprinting and signing. For password hashing, use bcrypt, scrypt, or argon2 — those are designed to be slow on purpose to resist brute force. SHA-256 is too fast (GPUs can compute billions per second), making it dangerous for password storage.

The three families

Family Examples Key size Where you'll see it
RSA RS256, PS256 2048–4096 bits Legacy JWTs (Google OIDC), older TLS certs
ECDSA ES256 (P-256), ES384 (P-384) 256–384 bits JWT/VC default — P-256 is everywhere
EdDSA Ed25519, Ed448 256 bits Modern systems, preferred for greenfield work

Key takeaways

  • ECC keys are way smaller than RSA for equivalent security. 256-bit ECC ≈ 3072-bit RSA. This is why mobile wallets, QR-based credentials, and SD-JWT compactness all favor ECC over RSA.
  • Ed25519 > ECDSA for greenfield work: no nonce-reuse footgun (see PlayStation 3 story below), faster, safer defaults.
  • But ES256 is everywhere in the VC/JWT ecosystem because it's the standardized default. You'll meet both algorithms in practice.

Nonce determinism — the PlayStation 3 story

ECDSA's signing math requires a random per-signature value called k (a "nonce"). The signature embeds it, so different k → different signature. Same (key, message) twice → two distinct signatures.

Ed25519, by contrast, derives k deterministically by hashing the private key with the message. Same inputs → same k → same signature, every time.

The footgun

If ECDSA ever reuses k for two different messages signed with the same key, the private key is mathematically recoverable from the two signatures. Sony's PlayStation 3 firmware signing was broken in 2010 exactly this way — they hard-coded k instead of using a fresh random value. Ed25519's deterministic construction makes this entire class of bug impossible.

The "never roll your own" rule

You use crypto.sign and crypto.verify. You never implement RSA, ECDSA, or SHA-256 yourself. Side-channel attacks (timing, power analysis, branch prediction) live in the implementation details — battle-tested libraries spend years closing those holes.

Self-check & further reading

Self-check

Try to answer before clicking "Show answer".

A signature proves ______ but does NOT prove ______.

A signature proves authenticity (the signer holds the private key) and integrity (the message hasn't changed). It does NOT prove confidentiality (signing isn't encryption), freshness (replays are still possible), or real-world identity (only key-possession; mapping keys to humans is the trust problem).

If SHA-256 had a known collision, what would the threat to a JWT be?

An attacker could craft a different payload that hashes to the same digest as a legitimate one — and a signature over the legitimate digest would also verify the malicious payload. Token forgery. (This is the integrity guarantee collapsing.) It's why post-quantum cryptography research focuses on collision-resistant hashes; SHA-256 is currently considered safe but algorithm migration plans exist (SHA-3, BLAKE3) for the day it isn't.

Ed25519 is preferred over ECDSA when ______ because ______.

Preferred for greenfield work because it has no nonce-reuse footgun (the k value is derived deterministically, so the PS3-style key recovery from reused nonces is impossible), is faster than ECDSA, and has safer defaults. Use ECDSA when you must — i.e., when an existing standard (like JWT's ES256) requires it.

Why does the same Ed25519 key produce the same signature every run, while ECDSA produces a different signature every run?

ECDSA's signing math requires a random per-signature value k (the "nonce"). The signature embeds k, so a different k produces a different signature. Ed25519, by design, derives k deterministically by hashing the private key and message together — same inputs always produce the same k and thus the same signature. This isn't just convenience; it eliminates the entire class of "reused nonce reveals the private key" bugs.

If you used RS256 instead of ES256, roughly how much larger would the signature be?

Roughly 4× larger. ES256 (ECDSA P-256) produces a 64-byte signature in raw form; RS256 (RSA-2048) produces a 256-byte signature. For RSA-4096 it's 512 bytes. This is the main reason QR-based credentials, NFC mDL transmissions, and mobile wallets all favor ECC — every byte counts in a QR code.
