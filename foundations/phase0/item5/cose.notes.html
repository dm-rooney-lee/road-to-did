05 — CBOR / COSE

The binary cousins of JSON and JWS. Same data model, much smaller wire footprint. CBOR is the serialization; COSE is signing/encryption on top. Required reading before mDL/mdoc (ISO 18013-5).

Background — read first

The shape of the family

Why a binary cousin

Wire size

~30–60% smaller than JOSE on typical payloads
JSON pays for whitespace, quoted keys, and base64url overhead. CBOR's length-prefixed binary, plus integer-keyed maps, removes most of that.

Constrained transports

NFC, BLE, QR
mDL/mdoc transmits over device-to-device channels with strict size budgets. JSON-based formats don't fit.

Constrained devices

IoT, smart cards, secure elements
CBOR is parseable without a UTF-8 stack, without a JSON tokenizer, in ~1 KB of code. Designed for environments where JSON.parse is too heavy.

Deterministic encoding

Signature-friendly
JSON has whitespace and key-order ambiguity. Signing canonicalized CBOR doesn't have that problem — there's exactly one canonical encoding per value.

Where you'll meet each in DID/VC

  • mDL / mdoc (ISO 18013-5) — CBOR-encoded credential wrapped in COSE_Sign1. The reason this item exists.
  • COSE_Key — how device-bound keys are conveyed in mdoc, side by side with JWK in mixed deployments.
  • WebAuthn / FIDO2 — attestation objects are CBOR; authenticator data is binary; cryptographic structures use COSE.
  • EUDI Wallet — supports both SD-JWT VC (JSON family) and mdoc (CBOR family). Real implementations need both.

The CBOR initial byte

Every CBOR value starts with one byte that packs two things:

┌───────────┬────────────────────┐
│  3 bits   │       5 bits       │
│ major type│  argument or marker│
└───────────┴────────────────────┘

The top 3 bits identify the major type (0–7). The bottom 5 bits are either the value itself (if it's small) or a marker telling the parser how many additional bytes follow as the "argument."

Argument size markers (bottom 5 bits)

Bottom 5 bitsArgument
0..23 (0x00–0x17)The argument IS this value. No additional bytes.
24 (0x18)Next 1 byte holds the argument.
25 (0x19)Next 2 bytes hold the argument (big-endian).
26 (0x1a)Next 4 bytes hold the argument.
27 (0x1b)Next 8 bytes hold the argument.

The major types this lab uses

MTTypeWhat the argument meansWhat follows
0 unsigned int the value itself (0..2^64-1) nothing
1 negative int encodes -(arg+1) nothing
2 byte string length in bytes arg bytes of payload
3 text string (UTF-8) length in bytes arg bytes of UTF-8
4 array number of items arg recursively-encoded values
5 map number of pairs arg pairs of (key, value), each recursive
6 tagged tag number one recursive value (the tagged content)

Major type 7 (simples / floats) exists but isn't used in this lab. Tagged values appear only as the outer wrapper of a COSE_Sign1 message — CBOR tag 18.

Negative int encoding (the trickiest case)

Major type 1 encodes negative integers, but the argument is positive. The actual value is -(arg+1). So:

  • -1 → arg = 0 → bytes 0x20
  • -7 (ES256 alg id) → arg = 6 → bytes 0x26
  • -100 → arg = 99 → bytes 0x38 0x63 (marker 24 → 1-byte arg)

The trick: -1 is the smallest in magnitude, so it pairs with arg = 0. As the negative number grows in magnitude, the argument grows.

The COSE message family

COSE defines six structures, all CBOR arrays with similar shapes. The lab only builds COSE_Sign1, the single-signer signed message — the binary parallel to compact JWS.

COSE_Mac0 MAC, one recipient (no signature, just integrity) JWS with HS256
COSE_Mac MAC, multiple recipients —

COSE_Sign1 structure

A four-element CBOR array, optionally tagged with CBOR tag 18:

tag(18) [
    protected:   bstr,              // CBOR-encoded map of "header parameters that MUST be signed"
    unprotected: map,               // header parameters that need NOT be signed (e.g. hints)
    payload:     bstr or nil,       // the bytes being signed (or nil if external)
    signature:   bstr,              // 64 bytes for ES256 (raw R‖S, not DER)
]

Three things worth flagging:

  • The protected header is wrapped in a bstr, not directly nested as a map. The bytes inside the bstr are themselves a CBOR-encoded map. This makes the protected header bytes byte-stable on the wire — receivers don't have to re-encode it to verify.
  • The signature is over the Sig_structure, not the array — see next tab.
  • The tag is optional. Some profiles emit tagged (mDL does); some emit untagged. Verifiers should accept both.

Sig_structure — what's actually signed

The signature in element[3] is NOT a signature over the array. It's a signature over a separate CBOR-encoded structure called Sig_structure (RFC 9052 §4.4):

Sig_structure = [
    context:        "Signature1",   // tstr — literal label for COSE_Sign1
    body_protected: bstr,           // same bytes as element[0] of the message
    external_aad:   bstr,           // additional authenticated data (often empty)
    payload:        bstr,           // same bytes as element[2] of the message
]

The signer:

  1. builds the protected header map and encodes it to bytes → body_protected
  2. builds the Sig_structure array above
  3. CBOR-encodes the array → to_be_signed
  4. signs to_be_signed with ES256 → 64-byte raw R‖S
  5. places the signature in element[3] of the COSE_Sign1 array

The verifier reconstructs the same Sig_structure from the received message, CBOR-encodes it, and verifies the signature against those bytes.

Why the indirection?

The literal string "Signature1" in the structure pins the algorithm context. If an attacker re-presented a COSE_Mac0 message as if it were a COSE_Sign1, the verifier would reconstruct with "Signature1" while the original was tied to "MAC0". Different to_be_signed bytes → signature fails. This is COSE's defense against algorithm/structure confusion — the binary cousin of JWS's alg discipline.

The external_aad slot lets the protocol bind additional context (e.g., a session ID) into the signature without putting it in the message. mDL uses this. Most simple cases pass an empty bstr.

~33% smaller. Most of the savings come from removing base64url overhead (every 3 bytes of binary become 4 bytes of text in base64) and from using integer keys (alg=1) instead of JSON strings ("alg":"ES256").

The signature itself is identical bytes in both — what differs is whether it's transported raw (COSE) or base64url-encoded (JWS).

Self-check & further reading

Self-check

Try to answer before clicking "Show answer".

What does CBOR's "initial byte" pack into its 8 bits?

Top 3 bits = major type (0–7), bottom 5 bits = either the value (0–23) or a marker (24/25/26/27) telling the parser that 1/2/4/8 more bytes follow as the argument.

CBOR can encode the integer 23 as either 0x17 (1 byte) or 0x18 0x17 (2 bytes). Both are valid CBOR. Why is this a problem for signed messages, and how does the lab's encodeCbor avoid it?

If an issuer signs the 1-byte form and a verifier re-encodes it as the 2-byte form (or vice versa), the Sig_structure to_be_signed bytes will differ and the signature won't validate. The fix is "core deterministic encoding" — always pick the shortest representation. The lab's encoder implements one rule per value, so it naturally produces deterministic output for the supported types.

Why is the COSE_Sign1 protected header wrapped in a bstr instead of being a direct CBOR map (like the unprotected one)?

Because the signature is computed over the protected header's bytes, not over the parsed map. Wrapping it in a bstr means those bytes are transmitted verbatim; the verifier doesn't have to re-encode anything (which could produce a different byte sequence and break verification). The unprotected header isn't signed, so its byte stability doesn't matter.

In COSE_Sign1, what gets fed to ECDSA to produce the signature — the four-element array, or something else?

Something else: the CBOR-encoded Sig_structure, which is the array ["Signature1", body_protected, external_aad, payload]. The literal string "Signature1" binds the signature to the COSE_Sign1 context (preventing structure confusion with COSE_Mac0, COSE_Sign, etc.). The four-element COSE_Sign1 array is the wrapper; the Sig_structure is what's actually hashed and signed.

CBOR map keys can be integers OR strings. Why does COSE consistently choose integers?

Wire size. { 1: -7 } (alg = ES256 in COSE) is 3 bytes. { "alg": "ES256" } is ~13 bytes in CBOR with string keys (or much larger in JSON). For mDL/mdoc and other transports with size constraints (NFC, BLE, QR codes), this matters. The trade-off is human readability — you can't eyeball a COSE message without a label registry.

A COSE_Sign1 message starts with 0xd2 0x84 ... Another one starts with 0x84 ... (no 0xd2). Are both valid?

Yes. The 0xd2 is CBOR tag 18, which indicates "the following CBOR value is a COSE_Sign1." It's optional per RFC 9052. Some profiles (mDL) require it. Many libraries emit it. Verifiers should accept both — strip the tag byte if present, then parse the array.
