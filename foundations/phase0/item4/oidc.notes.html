04 — OpenID Connect

OAuth gives you a token. OIDC adds an identity layer: ask for the openid scope and you also get an ID Token — a signed JWT that tells the relying party who logged in.

Background — read first

OIDC = OAuth + one new token + one new scope

OAuth 2.0 lets a client get an access token — a credential that says "the bearer is allowed to do X." That's authorization. It says nothing about who the user is.

OpenID Connect bolts identity onto OAuth by adding:

The openid scope

The opt-in switch
A single literal token added to the scope parameter of the authorization request. Without it, the OP runs plain OAuth. With it, the OP also mints an ID Token.

The ID Token

New deliverable
A signed JWT (you already built one in Item 02). Its payload is a standard claim set: iss, sub, aud, exp, iat, optionally nonce. Returned alongside the access token.

The nonce parameter

Replay protection
A random value the RP sends in the auth request. The OP embeds it in the ID Token's nonce claim. The RP checks it matches on receipt.

(Optional) Discovery

.well-known/openid-configuration
A JSON document at a well-known URL that tells RPs where the OP's endpoints live, which signing keys are in use, which scopes are supported, etc. Lets RPs auto-configure.

The ID Token claim set

An ID Token is just a JWS (which you can already build) whose payload follows OIDC's claim discipline. Five claims are mandatory.

ClaimRequired?Meaning
iss Required Issuer Identifier — URL of the OP, e.g. https://accounts.google.com. The RP checks this matches the OP it sent the user to.
sub Required Subject — stable identifier for this user at this issuer. Not an email; not human-readable in general. Same user across logins → same sub.
aud Required Audience — the client_id of the RP this token was issued for. Can be a string OR an array of strings; the RP must check its own client_id is in there.
exp Required Expiry — Unix seconds. The RP rejects the token if exp ≤ now. (Item 02 Lesson: seconds, not milliseconds.)
iat Required Issued At — Unix seconds. Useful for staleness checks ("don't accept tokens minted more than an hour ago even if exp is in the future").
nonce Required when sent If the RP put a nonce on the auth request, the OP MUST copy it here. RP checks payload.nonce === expectedNonce.
auth_time Optional When the user actually authenticated (vs when the token was issued). Lets RPs enforce "must have logged in within the last N seconds."
acr, amr Optional Authentication Context Class Reference / Methods Reference — how strong the authentication was (password? hardware key? MFA?).

What does "verifying an ID Token" actually mean?

Two stages, both required:
  1. Cryptographic check — the JWS signature verifies under the OP's public key, and header.alg is what the RP expects (e.g. ES256). This is exactly Item 02's verifyJwsCompact.
  2. Claim discipline — iss matches, aud contains your client_id, exp > now, nonce matches what you sent, sub is present.
A passing signature doesn't mean a trustworthy token. A token signed by the right key but issued for a different RP is still not yours.

Two opaque random values, two different jobs

Both are client-generated, both sent in the authorization request, both opaque. They live in different places at the end of the round trip and defend different attacks.

Mnemonic

state defends the redirect; nonce defends the token. State is wire-only — an attacker who couldn't see your session can't guess it. Nonce is token-bound — an attacker who captured a real token from one session can't reuse it in a new session whose nonce is different.

Discovery — preview only (not implemented in this lab)

Every OIDC provider publishes a JSON document at a fixed URL:

https://<issuer>/.well-known/openid-configuration

That document tells RPs everything they need to auto-configure: endpoint URLs, supported algorithms, and where to fetch signing keys.

{
  "issuer": "https://accounts.example.com",
  "authorization_endpoint": "https://accounts.example.com/oauth/authorize",
  "token_endpoint": "https://accounts.example.com/oauth/token",
  "userinfo_endpoint": "https://accounts.example.com/userinfo",
  "jwks_uri": "https://accounts.example.com/.well-known/jwks.json",
  "response_types_supported": ["code"],
  "id_token_signing_alg_values_supported": ["ES256", "RS256"],
  "scopes_supported": ["openid", "email", "profile"]
}

issuer

The OP's identifier. Must equal the iss claim in the ID Token. Verification rule: never trust an ID Token whose iss doesn't match the discovery doc you fetched.

jwks_uri

Where the OP publishes its public signing keys (as a JWK Set — see Item 02). The RP fetches this, picks the right key by kid, and verifies the ID Token signature with it.

authorization_endpoint

Where to send the user to log in. Same as OAuth — this is the URL your buildOidcAuthorizationUrl targets.

userinfo_endpoint

An optional endpoint the RP can call with the access token to fetch extra profile claims (email, name, picture) that didn't fit in the ID Token.

This lab doesn't implement discovery — it's mentioned so you recognize .well-known/openid-configuration when you meet it. In real RPs, fetching and caching the discovery doc is the first step of any new integration.

OAuth → OIDC: the URL diff

Side-by-side: the same authorization request, written as plain OAuth (Item 03) and as OIDC. The diff is small.

OAuth 2.0 — Item 03

https://issuer.example.com/oauth/authorize?response_type=code&client_id=wallet-app-42&redirect_uri=https%3A%2F%2Fwallet.example.com%2Fcallback&scope=email+profile&state=xyz-csrf-abc&code_challenge=…&code_challenge_method=S256
response_type=code client_id=wallet-app-42 redirect_uri=https://wallet.example.com/callback scope=email profile state=xyz-csrf-abc code_challenge=… code_challenge_method=S256

OIDC — Item 04

https://issuer.example.com/oauth/authorize?response_type=code&client_id=wallet-app-42&redirect_uri=https%3A%2F%2Fwallet.example.com%2Fcallback&scope=openid+email+profile&state=xyz-csrf-abc&code_challenge=…&code_challenge_method=S256&nonce=n-0S6_WzA2Mj
response_type=code client_id=wallet-app-42 redirect_uri=https://wallet.example.com/callback scope=openid email profile state=xyz-csrf-abc code_challenge=… code_challenge_method=S256 nonce=n-0S6_WzA2Mj

Two changes total: openid added to scope, and a new nonce parameter. Everything else is unchanged from Item 03.

What you get back is different though. Without openid: just an access token. With openid: an access token AND an ID Token whose nonce claim equals the value you sent here.

Self-check & further reading

Self-check

Try to answer before clicking "Show answer".

An RP sends an authorization request to an OP with scope=email profile (no openid). The user logs in. What does the RP get back?

Just an OAuth access token. No ID Token. The OP runs a plain OAuth flow because openid isn't in scope — the request was never an OIDC request. The user is authenticated to the OP, but the OP doesn't return identity claims to the RP. (Whether the access token can be used to call /userinfo depends on the OP's policy, but no ID Token is minted.)

An attacker captures a valid ID Token from session A and replays it into a new RP session B. Which check stops them, and why does it work?

The nonce check. Session A's RP sent nonce_A; the OP baked nonce_A into the signed token. Session B's RP sends a fresh nonce_B and expects to see nonce_B in the token. The captured token's nonce is nonce_A ≠ nonce_B. The attacker can't change it because the nonce is inside the signed payload — modifying it would break the signature.

An ID Token has a perfectly valid signature under the OP's public key, but its aud is "some-other-client". Should you trust it?

No. The signature being valid only means the OP minted it — it does NOT mean the OP minted it for you. The aud claim is the OP saying "this token is for client X." If your client_id isn't in aud, the token belongs to a different RP. Accepting it would let any other RP that uses the same OP impersonate users to your service.

Why is the ID Token a JWT (i.e. a JWS), but the access token usually treated as opaque even when it happens to be a JWT?

Different audiences. The ID Token is FOR THE CLIENT — the RP needs to read it to learn who the user is, so it has to be a structured, verifiable format (JWT/JWS). The access token is FOR A RESOURCE SERVER — the client just forwards it; only the resource server reads and verifies it. If a client introspects an access token as if it were for them, they'll accept tokens issued for other audiences and treat the user as logged in when they aren't.

Why does nonce have to be inside the signed payload, but state can live on the redirect URL?

Because they defend different things. state just needs to round-trip through the user's browser to prove the callback came from the session that started the flow — an attacker forging a callback can't guess it. It doesn't need to be unforgeable by the OP, because the OP isn't the attacker here.

nonce needs to be cryptographically bound to the token itself. Otherwise an attacker who captured a valid token could replay it into a new session — there'd be no way for the RP to tell "this token was for session A, not the session I'm currently in" unless the binding survives inside the signed payload.

In the OIDC discovery document, what's the relationship between issuer and the iss claim of an ID Token?

They must be identical. The RP fetches discovery from https://<issuer>/.well-known/openid-configuration and gets back a JSON object whose issuer field is the OP's canonical identifier. Every ID Token that OP mints must have iss equal to that string. If they don't match — say, you fetched discovery from one URL but got a token claiming a different issuer — somebody is lying. This is the chain that ties "the OP I think I'm talking to" to "the key I'll verify signatures with" to "the claims I'll trust."
